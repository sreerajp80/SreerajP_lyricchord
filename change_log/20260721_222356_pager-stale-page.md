# Fix: performance view showed the wrong song after saving an edit

Implements [plans/20260721_221911_pager-stale-page.md](../plans/20260721_221911_pager-stale-page.md).

## The bug

After editing and saving a song, the performance view could show one song's
title in the top bar and a *different* song's lyrics and key below it.

Why: the song list sorts "newest activity first", so saving a song bumps its
timestamp and moves it to the top. The performance view's swipe pager is
built from that list. The old code tried to handle the reorder by creating a
new `PageController` with the right `initialPage`, but Flutter's `Scrollable`
keeps the existing scroll position and simply re-attaches it to the new
controller — `initialPage` was never applied. The pager stayed at the old
pixel offset, which now belonged to a different song. Because the page number
did not change, `onPageChanged` never fired, so the title (driven by
`_currentId`) and the visible sheet disagreed.

(The plan's first idea, `keepPage: false`, was tried and did not fix it — the
regression test proved that. The plan file records the correction.)

## What changed

- `lib/screens/song_performance_screen.dart` — `_syncPager` now keeps one
  `PageController` for the life of the screen. When the song list changes
  under a live pager, it jumps back to the current song's new index in a
  post-frame callback. This also stops disposing a controller that was still
  attached to the pager.
- `test/screens/song_performance_screen_test.dart` — new regression test
  "stays on the same song after a save reorders the list", plus a
  `sheetText` helper that reads the lyric text the sheet is actually drawing.

## Checks

- `flutter analyze` — no issues.
- `flutter test` — all 175 tests pass.
- `dart format` — run on both changed files.

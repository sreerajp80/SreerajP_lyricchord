# The app can now read published Carnatic notation

Date: 2026-08-22

Implements [plans/20260822_000000_carnatic_notation_import.md](../plans/20260822_000000_carnatic_notation_import.md).

---

## Why

`docs/carnatic_notation.md` described how published notation works and how it
maps onto our `{melody}` format. **The app implemented almost none of it.** The
sample song had a correct melody only because it was converted by hand, outside
the product, with throwaway scripts in a temporary folder. A musician pasting
notation from a published page got `Could not read ";"`.

The app contained one converted song, not the ability to convert. It does now.

## What was built

### `lib/services/carnatic_notation_import_service.dart` — new

Converts a block of published notation into `{melody}` lines, applying the §4
rules: `;` = two aksharakalas, `,` = one, uppercase note = two, lowercase = one,
underlined runs packed faster, letters written together sharing a beat, `-` and
`*` carrying no time, octave dots.

Durations are counted in **quarter-aksharakalas**. That grain exists because an
underlined run halves everything inside it and a lowercase note is already the
shortest thing there is — halving it needs somewhere to go. Integers throughout,
so nothing rounds.

**The two conventions are told apart, not assumed.** §4a says letter case means
duration on some pages and octave on others, and only the page's legend or the
tala arithmetic can separate them. The service converts under both readings,
scores each against the tala, and returns the winner with the score. On the
sample song's pallavi that reads `duration: 4/4` against `octave: 1/4`.

The two readings also count in different grains — where case carries duration
the unit is the aksharakala, where it carries the octave every written note is a
whole beat. Getting that wrong made the first attempt score both on one scale
and pick wrongly; it is now explicit in `_unit()`.

**It will not choose between the madhyamams.** That is raga grammar (§5), varies
per raga, and the notation does not mark it. `applyAnyaSvaraRule` is off by
default; either way the positions of the `Ga -> Ma -> Ri` phrase come back as
hints.

### `lib/models/carnatic_import_result.dart` — new

The converted lines plus the evidence: which reading was chosen, how each
scored, what did not add up, where the anya-svara phrase appears. `isAmbiguous`
is true only when both readings fit **and** fit equally — equal scores of zero
are two failures, not a tie, and are reported as such.

### `lib/widgets/carnatic_notation_sheet.dart` — new

Paste, see the conversion, insert. Shows which reading was used and how well it
landed, what the other reading scored, every problem, and a switch for the
bhashanga madhyamam rule. Insert stays disabled until something converts.

### `lib/screens/song_editor_screen.dart`

**More options -> Paste Carnatic notation.** The menu previously appeared only
for saved songs; it now appears for new ones too, since importing notation is
most useful while writing. "Save as copy" stays conditional.

The tala comes from the song's own `{tala: ...}` line. Without one there is
nothing to check the cycles against, so the user is told rather than handed a
silent wrong answer.

### `{sruti: madhyama}`

`ParsedSheet.isMadhyamaSruti`, and `_melodyTonicHz` places Sa five semitones up
for such a song. Some ragas are sung with the tambura's Pa string dropped to
shuddha madhyamam, and that note taken as the base Sa — so the written Sa is not
the singer's adhara shadja. Without this the melody player hums the tune a
fourth too low against the drone, which is the exact bug that made the first
transcription of the sample song wrong. The sample song now declares it.

### `lib/services/melody_parser_service.dart`

`;` accepted as a synonym for `,` — in the source convention it is two
aksharakalas, which is one beat, the same thing our `,` means. A trailing `*` is
stripped rather than making a note unreadable.

## The sample song is now generated by the product

The 32 melody lines were **regenerated by the importer** and pasted back into
`app_database.dart`. They differ from the hand-converted ones only in dropping
cosmetic padding — `Ga3-,` where `Ga3` says the same thing. Musically identical,
and now reproducible by code that ships.

## Not built — still open

From the plan's list, items 3 to 5 remain, and are recorded in
`docs/carnatic_notation.md` §8:

* **Sangatis** have no *label* — see the correction at the end of this log.
* **A beat is atomic** — 5 notes of 397 in the sample were snapped by half a
  beat.
* **`!` and `~` are not sounded** — still phase 3 of the melody feature.

Also unresolved, and musical rather than technical: in an ascending run like
`nsrgmp` the leading `n` may belong in the lower octave. The source writes no
dot, so it is transcribed in the middle octave as written. A musician's ear
would settle it.

# Correction — sangatis can be stacked after all

Date: 2026-08-22

The plan, this log and `docs/carnatic_notation.md` all stated that stacking
sangatis would make the player "run them together as one long melody", and that
they therefore had to be pasted one at a time. **That is wrong.**

Checked in the code: `MelodyPlayerNotifier.play()` takes a single `MelodyLine`,
and `MelodyLineRow` draws one row with its own play button per `{melody}` line.
Playback is per line. Several sangatis stacked under one lyric line each play
independently; nothing joins them.

What is actually missing is only a **label** — the format cannot mark one line as
a variation of another. A plain text heading solves that today, because section
headings are ordinary lines:

```
Pallavi:
[Sa]krishna nee bEganE baarO
{melody} , , Sa | Ga3 Ma1 | Ri2 ,

Sangati 2:
{melody} , , Sa | Ga3 Ma1 | Ri2 ,
```

No code change needed. Section 6 and the limits list in section 8 of the
document have been corrected. The seeded sample still carries the first sangati
only, which is a choice about that song rather than a limit of the format.

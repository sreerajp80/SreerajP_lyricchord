# Store the song tradition properly (raga, tala, tradition)

Implements [plans/20260809_130652_song-tradition-storage.md](../plans/20260809_130652_song-tradition-storage.md).

## What was wrong

The app already kept Western and Indian songs apart, but it worked that out by
re-reading the `{raga: …}` header line inside the lyrics every time. Nothing was
stored. Four problems came from that:

1. Raga and tala were not columns. Every read re-parsed the whole song, and the
   editor had no field for them — the user had to know the curly-brace syntax.
2. A typo silently damaged data. `{ragam: …}` is not `{raga: …}`, so the song
   looked Western, and a transpose then rewrote `[Ga]` and `[Dha]` as the chords
   G and D. No warning, no undo.
3. A song with a raga but no readable tala fell back to the user's global "Pitch
   naming" setting, so the same song read Carnatic on one phone and Hindustani
   on another.
4. Nothing warned when a raga was paired with a tala from the other tradition.

## What changed

### Storage (schema version 8 → 9)

Three columns added to `song_notes`:

| Column | Default | Meaning |
|---|---|---|
| `raga` | `''` | Raga name; empty on a Western song |
| `tala` | `''` | Tala name; empty on a Western song |
| `tradition` | `''` | `western`, `carnatic`, `hindustani`, or empty = not classified |

The migration reads each song's existing header lines, classifies it once, and
writes the answer in. It **does not touch the lyrics text** — the header lines
stay where the user put them, and the parser keeps hiding them from the sheet,
so nothing on screen changes after the upgrade.

Two details worth noting:

- The backfill uses a targeted `update(...).write(...)`, not `replace()`, so
  `timestamp` is left alone and the songbook does not reorder itself.
- The column-adding step checks `PRAGMA table_info` first. Adding a column that
  already exists is a hard SQLite error, which would leave the upgrade
  half-applied and the app unable to open.

The same backfill also runs on `onCreate`, so a fresh install and an upgraded
one classify the seeded songs identically.

### The rule, unchanged but now stored

- **Western vs Indian** — the `tradition` column, read through
  `SongNote.isIndian`. When it is null, it falls back to the old "does it name a
  raga" rule.
- **Carnatic vs Hindustani** — still the **tala**, not the raga
  (`PitchNamingService.detect`). This was already right: tala names split
  cleanly between the traditions, while many raga names are shared.

### Reading

`ChordTransposer.transposeLyrics` and `chordsUsed` take a new optional
`isIndian` flag. When given, it wins; the text sniff is only a fallback for
imported text that has no song row yet. The PDF export and the performance
screen now pass the song's stored value.

### Editor

- A **Notation** dropdown (Western / Carnatic / Hindustani).
- Western shows the **Original key** field; either Indian tradition replaces it
  with **Raga** and **Tala**.
- Switching back to Western clears the raga and tala, so a stale value cannot
  make the song look Indian again.
- A tala from the other tradition shows a warning under the field. Advice only —
  saving is never blocked.

### Import / export

- `ChordProService.parse` and `parseMultiple` read `{raga:}` and `{tala:}` into
  the columns and set the tradition.
- `format` writes them from the columns, and **skips the `{key: …}` line for an
  Indian song** — it was writing a meaningless key on every swara sheet. The PDF
  export already avoided this.
- Old `{raga:}` / `{tala:}` lines still sitting inside the lyrics are dropped on
  export so they are not written twice.
- AirQR sends songs as ChordPro text, so it inherits the fix.

## Deviation from the plan

The plan called for a `traditionsAgree(raga, tala)` check. That is not
implementable as written — the app has no raga-to-tradition table, and building
one would be guesswork because raga names are shared across the traditions.

Implemented instead: `PitchNamingService.talaMatchesTradition(tala, tradition)`,
which compares the typed tala against the tradition the user picked. This is
checkable, is a real mismatch when it fires, and returns `null` ("no opinion")
for an empty tala, an unknown tala, or a Western song.

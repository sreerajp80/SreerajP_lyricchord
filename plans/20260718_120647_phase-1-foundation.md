# Plan — Phase 1: Foundation (data, theme, seeding)

**Status:** completed

## What this phase delivers

Phase 1 from [../docs/implementation_plan.md](../docs/implementation_plan.md):
local storage, the Material 3 violet theme, and the three seeded songs — the
base every later screen needs.

Definition of Done (from the plan):

- App opens the database, seeds on first run, and applies the saved theme.
- Repository unit tests pass against an in-memory drift database.

## The issue / gap

Phase 0 left only a placeholder `HomeScreen` with a default seed theme and no
database. There is no `SongNote` model, no drift database/DAO, no repository, no
real theme, and no theme-mode persistence. Phase 1 fills all of that in.

## Source of truth for data

Ported 1:1 from the existing Android app (`L:\Android\lyriccord`):

- `SongNote` fields: `id, title, artist, lyrics, key, bpm, favorite, timestamp`
  (see [../docs/architecture.md](../docs/architecture.md) §11).
- Table name `song_notes`, schema version 1.
- The three seed songs (exact title/artist/key/bpm/lyrics/favorite) come from
  the Android `AppDatabase.kt` prepopulate callback. Amazing Grace is starred.
- Violet "High Density" palette from the Android `Color.kt` / `Theme.kt`
  (primary `#6750A4` light / `#D0BCFF` dark, backgrounds `#FDF8FD` / `#141218`).

## Files to change / create

### New — model
- `lib/models/song_note.dart` — immutable `SongNote` (final fields, `copyWith`,
  `==`/`hashCode`). No drift imports here (keep the domain model pure).

### New — data (drift)
- `lib/data/app_database.dart` — drift `@DriftDatabase` with a `SongNotes`
  table (columns matching `SongNote`), schema version 1, and the DAO methods:
  `watchAllSongs()` (ordered by `timestamp DESC`), `watchSongById(int)`,
  `insertSong`, `updateSong`, `deleteSong`, plus a `_seedIfEmpty()` run from the
  `MigrationStrategy.beforeOpen` (seed only when the table is empty on first run).
- `lib/data/app_database.g.dart` — generated by `build_runner` (not hand-edited).
- The table `favorite` (bool) and `timestamp` (int, ms since epoch, default =
  now) map straight to Dart `bool`/`int`.

> Note: Android used db file `song_notes_database`; the Flutter app uses
> `AppConstants.databaseName` (`lyriccord.db`) — a fresh install, so no
> migration from the Android file is needed. Table name stays `song_notes`.

### New — repository
- `lib/repositories/song_repository.dart` — `SongRepository` wrapping the DAO,
  exposing `Stream<List<SongNote>> watchAllSongs()`,
  `Stream<SongNote?> watchSongById(int)`, and `insert/update/delete`. Converts
  between drift rows and the pure `SongNote` model so callers never see drift
  types. Wraps DB errors in `StorageException`.

### New — errors
- `lib/core/errors/app_exception.dart` — the sealed `AppException` hierarchy
  with `StorageException` (used now), plus `ImportException` / `ExportException`
  stubs for later phases (per architecture §10). Keeps future phases from
  re-touching this file.

### New — theme
- `lib/theme/app_colors.dart` — the raw palette constants (light + dark) from
  the Android `Color.kt`.
- `lib/theme/app_theme.dart` — `AppTheme.light()` / `AppTheme.dark()` building
  Material 3 `ThemeData` from a `ColorScheme` using those role colours, matching
  the Android `Theme.kt` mapping.

### New — providers
- `lib/providers/database_provider.dart` — `appDatabaseProvider` and
  `songRepositoryProvider`. `appDatabaseProvider` is defined to `throw
  UnimplementedError` and is **overridden** in `main()` with the opened DB (so
  tests can override with an in-memory DB). Repository is derived from it.
- `lib/providers/theme_mode_provider.dart` — a `Notifier<ThemeMode>` that reads
  the saved mode from `shared_preferences` (`AppConstants.prefThemeMode`) and
  writes on change. A `sharedPreferencesProvider` is overridden in `main()`.

### Change — app entry
- `lib/main.dart` — new init sequence (architecture §5):
  1. `WidgetsFlutterBinding.ensureInitialized()`
  2. Open the drift database (seeds on first run)
  3. Read `SharedPreferences`
  4. Build `ProviderScope` with overrides (db + prefs)
  5. `runApp`
  `LyricCordApp` becomes a `ConsumerWidget` that watches `themeModeProvider` and
  passes `AppTheme.light()/dark()` + the mode into `MaterialApp`.

### New — tests
- `test/repositories/song_repository_test.dart` — against an **in-memory** drift
  database (`NativeDatabase.memory()`): seeding happens on first open (3 songs,
  Amazing Grace starred); insert/update/delete; `watchAllSongs` ordered by
  timestamp desc; `watchSongById` returns the right song / null.
- `test/helpers/` — a small helper to build an in-memory `AppDatabase` if useful.

### Change — docs (after implementation)
- `docs/implementation_progress.md` — tick Phase 1 boxes and flip its status.

## Conventions I will follow

- `package:` imports (per CLAUDE.md hard rule), not relative — even though the
  Phase 0 files used relative imports.
- Immutable model with `copyWith`; widgets/repository never mutate in place.
- No networking, no new blocked packages. `drift` + `sqlite3_flutter_libs` +
  `shared_preferences` are already in `pubspec.yaml`.
- Run `dart run build_runner build --delete-conflicting-outputs`, then
  `flutter analyze` (zero warnings) and `flutter test` before finishing.

## Out of scope (later phases)

- The songbook list UI, search, filter, favorite/delete UI (Phase 2) — Phase 1
  keeps the placeholder home screen but under the real theme.
- Editor, performance view, transpose, chord diagrams, import/export.

## Risks

- drift codegen must succeed; if `build_runner` fails I stop and report rather
  than hand-editing generated files.
- Seeding must run exactly once (only when the table is empty) so a user's real
  songs are never overwritten.

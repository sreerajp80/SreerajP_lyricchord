# Plan: Create the core docs (architecture, implementation plan, security)

**Status:** completed

## What the issue is

The idea doc ([../docs/lyriccord_idea.md](../docs/lyriccord_idea.md)) captures
the "why and what" of the LyricCord Flutter conversion. Before Flutter code is
written, the project still needs the "how" documents that the docs-folder
guideline lists as core: the **architecture** (filled-in blueprint), a
**phase-by-phase build plan**, and a short **security** posture.

Given inputs from the user:

- App id / namespace: `in.sreerajp.lyriccord`
- Toolchain: Flutter 3.41.9 (stable), Dart 3.11.5

## Which profiles apply (drives which docs)

From `GUIDELINES_MANIFEST.md`:

- **Core Baseline** — always. → `architecture.md`.
- **Production App Extension** — yes, this ships to users. → `release_process.md`
  and build flavors apply *later*; for now we only link to them.
- **Sensitive Data Extension** — **no.** LyricCord is a fully offline, local-only
  songbook with no secrets, PII, health, or finance data. So a full `security.md`
  blueprint is not required. We will still add a **short** `security.md` recording
  the offline / no-INTERNET-permission posture, because that stance is worth
  writing down and is easy to verify.

## Plan for the fix (what I will create)

Three new files under `docs/`, each following the guideline anatomy (H1 title
with app name, purpose paragraph, "Read first" relative links, `---` separators,
numbered `##` sections, simple English):

1. **`docs/architecture.md`** (Living) — filled in from
   [../docs/guidelines/architecture.md](../docs/guidelines/architecture.md).
   Sections that do not apply will be marked `N/A` with a one-line reason
   (the blueprint tells us to do this rather than invent content).

2. **`docs/implementation_plan.md`** (Point-in-time, has a `**Date:**` line) —
   one `##` per phase, mirroring the 8 phases in the idea doc, each with an
   Objective, Action steps, and a Definition of Done.

3. **`docs/security.md`** (Living, short) — offline boundary, no INTERNET
   permission, minimal permissions, input handling for imported ChordPro files,
   and a note that the full Sensitive-Data blueprint does not apply. Links to the
   submodule template for the full checklist.

## Key decisions to confirm (please review)

These are my proposed technical choices for `architecture.md`. Tell me if you
want different ones before I write:

| Topic | Proposed choice | Why |
| --- | --- | --- |
| Structure tier | **Tier 1**, baseline `lib/` layout from `guideline.md` §3 | One feature area (songbook); small app |
| State management | **Riverpod** | Reactive, replaces the Android `ViewModel` + `StateFlow` cleanly |
| Local database | **drift** | Reactive queries mirror Room's `Flow`; the list/detail views need live updates |
| Key–value store | **shared_preferences** | Just the theme-mode setting |
| Navigation | **go_router** | Small route set (list / detail / editor) |
| PDF export | **`pdf` + `printing`** packages | Replaces the Android `PdfDocument` canvas export |
| Platforms | **Android + iOS** (desktop optional later) | Matches the idea doc |

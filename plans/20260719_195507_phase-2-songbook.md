# Phase 2 — Songbook (list screen)

**Status:** completed

**Date:** 2026-07-19

Implements Phase 2 of [docs/implementation_plan.md](../docs/implementation_plan.md).

---

## 1. What is missing (the issue)

Phase 1 gave us the database, the seeded songs, the theme, and the repository.
But the app still opens a placeholder screen (`lib/screens/home_screen.dart`)
that just says "Your songbook is coming soon."

There is no way to see the songs, search them, star them, or delete them. There
is also no router yet, even though `go_router` is already a dependency and
[docs/architecture.md](../docs/architecture.md) §13 lists the routes.

## 2. Scope of this phase

From the plan, Phase 2 must give us:

- A song list of cards showing title, artist, key badge, BPM badge.
- Search over title, artist, and lyrics (filtered in memory).
- An **All / Starred** filter row with live counts.
- A star toggle and a delete action on each card.
- An empty state.
- A floating **+** button to start a new song.
- Responsive: single pane below 600 dp, dual pane at 600 dp and above.
- An overflow menu with **Import ChordPro** (disabled placeholder until Phase 7)
  and the three theme choices.

**Not in this phase:** the editor (Phase 3), the performance view (Phase 4), and
real ChordPro import (Phase 7). Where Phase 2 needs to navigate to those, we add
a small "coming soon" placeholder screen so the app never dead-ends.

## 4. The plan in detail

### 4.1 Router (`lib/core/router/app_router.dart`)

- A `goRouterProvider` (Riverpod `Provider`) returning a `GoRouter`.
- Routes exactly as architecture §13 lists them. `/song/:id`, `/song/:id/edit`
  and `/new` all point at the placeholder screen for now.
- `main.dart` switches to `MaterialApp.router`.
- Keeping the router in a provider means Phase 3 and 4 only swap the builders.

### 4.2 List state (`lib/providers/song_list_provider.dart`)

- `songsStreamProvider` — a `StreamProvider<List<SongNote>>` from
  `SongRepository.watchAllSongs()`.
- `searchQueryProvider` — a `NotifierProvider<String>` holding the search text.
- `songFilterProvider` — a `NotifierProvider<SongFilter>` where `SongFilter` is
  an `enum { all, starred }`.
- `filteredSongsProvider` — a plain `Provider` that reads the three above and
  returns the visible list. Search is case-insensitive and matches title,
  artist, or lyrics. Filtering is in memory, as architecture §11 states.
- `songCountsProvider` — returns the total count and the starred count, so the
  filter row updates live.
- `selectedSongIdProvider` — which song the tablet right pane shows.

All of this is pure Dart over a list, so it is easy to unit test.

### 4.3 Songbook screen (`lib/screens/song_list_screen.dart`)

Top to bottom, matching [docs/lyriccord_idea.md](../docs/lyriccord_idea.md) §3.1:

1. `AppBar` with the "LyricCord" wordmark and the "Lyrics & Chords Notebook"
   subtitle, plus an overflow menu holding **Import ChordPro** (shown disabled,
   wired in Phase 7), the three theme choices, and **About**.
2. The search field.
3. The All Songs / Starred filter row with counts.
4. `ListView.builder` of `SongCard`s (builder, per the engineering standard's
   list rules).
5. The empty state when the list is empty — different wording for "no songs at
   all" and "nothing matched your search".
6. A `FloatingActionButton` that goes to `/new`.

Delete asks for confirmation in a dialog first, then shows a `SnackBar`. Star
toggling is immediate. Any `StorageException` from the repository is caught and
shown as a `SnackBar` — never a crash (hard rule 4).

### 4.4 Responsive shell (`lib/screens/home_shell.dart`)

- `LayoutBuilder` on `AppConstants.tabletBreakpoint` (600).
- Below 600 dp: just the list; tapping a card navigates to `/song/:id`.
- At or above 600 dp: a `Row` with the list at 38% and the detail pane at 62%,
  matching the idea doc. Tapping a card sets `selectedSongIdProvider` instead of
  navigating. With nothing selected the right pane shows a welcome state.

### 4.5 Repository addition

```dart
Future<void> toggleFavorite(SongNote song);
```

It calls `update` with `favorite` flipped. This keeps the "widgets know no SQL"
rule and gives Phase 2 one clear call.

## 5. Rules this plan follows

- Layer order stays `Widget → Provider → Repository → DAO` — no widget touches
  drift or SQL.
- No new packages. Nothing added is networked (fully offline stays true).
- Files `snake_case`, providers end in `Provider`, `package:` imports, `const`
  where possible.
- Tests mirror `lib/`, and the new provider and widgets each get a test.

## 6. How we will check it is done

- `flutter analyze` is clean.
- `flutter test` passes, including the new tests.
- Manual run: search, star, unstar, filter, delete, counts update live; the
  layout switches to dual pane when the window is widened past 600 dp.

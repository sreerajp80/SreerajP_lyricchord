# Plan — Create CLAUDE.md for LyricCord

**Status:** completed

## The issue

The project has no `CLAUDE.md` at its root. Claude Code reads `CLAUDE.md` at the
start of every session, so without it the AI has no project-specific rules,
identity, or pointers to the `docs/` set. The user asked to create one based on
the two guideline documents (`CLAUDE_MD_GUIDELINE.md` and
`DOCS_FOLDER_GUIDELINE.md`).

## Profile decision

**Thin pointer profile.** The project already has a full `docs/` folder
(`architecture.md`, `security.md`, `implementation_plan.md`, `lyriccord_idea.md`,
`GUIDELINES_MANIFEST.md`) plus the shared `guidelines/` submodule. Per the
guideline, a project with a docs set uses the Thin profile: `CLAUDE.md` gives
identity, commands, and a short rule summary, and links to `docs/` for detail
instead of repeating it.

## Files to change

- **Create** `CLAUDE.md` at the project root. (One new file only.)

No other project files are touched.

## The plan for the file

Write `CLAUDE.md` following the canonical section order (§2) and the "Always"
section checklist (§3) of the guideline, in this order:

1. **Title + read-first banner** — auto-loaded, read before any change.
2. **Project identity table** — filled with real values from `architecture.md`:
   app name LyricCord; lyrics & chords notebook; Android + iOS (min SDK 24);
   package `in.sreerajp.lyriccord`; Flutter 3.41.9; Dart 3.11.5; Riverpod;
   go_router; drift (SQLite) + shared_preferences; fully offline (no INTERNET).
3. **Read these docs before working** — Thin-profile table pointing to
   `docs/architecture.md`, `docs/security.md`, `docs/implementation_plan.md`,
   `docs/lyriccord_idea.md`, `docs/GUIDELINES_MANIFEST.md`, and key
   `docs/guidelines/…` references.
4. **Hard rules** — offline-first (no INTERNET permission / no network package);
   like-for-like port, no redesign; no AI features; never crash on bad import;
   scoped storage only (system file picker, no broad storage permission).
5. **Architecture rules** — Tier 1 layered `lib/` layout; the data-flow
   dependency direction; widgets must not know SQL/ChordPro/PDF; link to
   `architecture.md`.
6. **Build & run commands** — copy-paste `flutter pub get`, `run`, `analyze`,
   `test`, `dart format`, drift `build_runner`, and release APK/appbundle
   (single flavor, so no `--flavor`).
7. **Signing / keystore** — never commit keystore / `key.properties`; link to
   guideline; note `.gitignore` entries. (App is meant to ship.)
8. **Security rules** — never log song content in release; no runtime
   permissions; no INTERNET; validate imported ChordPro defensively; link to
   `docs/security.md`.
9. **Code style / naming** — snake_case files, PascalCase classes, `camelCase`
   + `Provider` suffix; `package:` imports; `const`/`final`; zero-warning
   `analyze`; do not edit generated `*.g.dart` / drift generated files.
10. **Testing rules** — mirror `lib/` in `test/`; name the critical areas
    (transpose, ChordPro round-trip, chord-over-lyric parsing, Tempo-Auto scroll
    math, first-run seeding); link to `architecture.md` §18.
11. **Dependency constraints** — blocked: any networking / cloud / analytics /
    AI package (offline app); check a new package for network deps first.
12. **Where things live** — short project tree.
13. **Workflow rules** — inline plan → approve → log (verbatim in spirit, per
    guideline §5).
14. **Communication rules** — inline simple-English rule (verbatim in spirit).
15. **What Claude must always / never do** — short dos & don'ts.

All detail that already lives in `docs/` is linked, not duplicated (Thin rule).
All cross-links use relative paths.

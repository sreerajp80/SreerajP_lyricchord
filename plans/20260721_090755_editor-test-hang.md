# Plan — Fix the hanging editor screen tests

**Status:** completed

**Date:** 2026-07-21

Fixes the `test/screens/song_editor_screen_test.dart` tests that hang for 10
minutes each (and one that fails fast), which make `flutter test` take ~30
minutes and look stuck.

---

## 1. What is wrong (facts gathered)

Running `test/screens/song_editor_screen_test.dart`:

- **Pass:** the first four tests (open new, open existing, suggestions follow
  key, tapping a chord inserts it).
- **Fails fast:** "a custom chord is added to the toolbar" — the finder for the
  dialog's `FilledButton` "Add" finds nothing, so the custom-chord dialog did
  not open in that run (line 88).
- **Hangs (10-minute timeout):** "saving a new song stores it", "editing an
  existing song updates it", and "cancel asks before throwing edits away". Each
  hangs on the `pumpAndSettle()` that runs **after** tapping an app-bar action
  (Save or the close button).

Confirmed by experiment: the same hang happens on the **committed HEAD**
(`6a92e7e`, Phase 3) after reverting the two uncommitted work-in-progress files.
So the hang is **pre-existing** and was **not** caused by the uncommitted change
(swapping `watchSongById().first` → `findById()` in the editor provider's
`build()`), which was a partial attempt to deal with it.

Ruled out by evidence:

- **Not the text-cursor blink.** Tests that focus a text field and even open an
  `autofocus` dialog (e.g. "tapping a chord", the custom-chord dialog) return
  from `pumpAndSettle()` fine. So a focused field is not what hangs it.
- **Not the uncommitted WIP.** HEAD hangs too.

Still unknown: the exact widget/animation that keeps scheduling frames after the
Save/close tap. The only continuous-frame widget in the editor subtree is the
`CircularProgressIndicator` in the provider's `loading` branch
([lib/screens/song_editor_screen.dart:106](../lib/screens/song_editor_screen.dart#L106)),
so the leading theory is that the editor's `AsyncNotifier` re-enters its
`loading` state during those actions, but this is not yet proven.

## 2. Why it matters

- `flutter test` takes ~30 minutes and looks hung, which blocks the normal
  "run analyze + tests after a change" workflow.
- Three real user flows (save new, save edit, cancel-with-changes) have no
  working test cover.

## 3. Fix plan

Because the exact frame source is not yet proven, step A **finds** it before any
fix, so we fix the real cause instead of masking it.

### Step A — Root-cause probe (temporary, removed before finishing)

- Add a short throwaway test that reproduces the Save flow but pumps in a
  **bounded** way (`await tester.pump(const Duration(milliseconds: 16))` a fixed
  number of times, never `pumpAndSettle`). After the Save tap, read and print
  `tester.binding.hasScheduledFrame`, `tester.binding.transientCallbackCount`,
  and any pending timers, to see what keeps scheduling frames.
- Run it with a **hard 60-second timeout** so it can never hang the suite.
- This tells us whether it is the loading spinner, a stuck route/overlay
  animation, an infinite rebuild loop, or a leaked timer.

### Step B — Fix the real cause (one of)

Depending on what Step A shows, apply the matching fix:

- **If the provider re-enters `loading`** (spinner runs forever): stop the editor
  screen dropping into the full-screen spinner once it has data — keep showing
  the last draft while a rebuild is in flight (e.g. use `draftAsync.valueOrNull`
  / a "has been filled" guard) so there is no perpetual `CircularProgressIndicator`.
- **If it is an infinite rebuild / state loop** in `_save` or `_close`: break the
  loop (guard the state write, or stop watching what it writes).
- **If it is a genuinely unavoidable ongoing animation in the app**: change the
  three tests to pump in a bounded way instead of `pumpAndSettle()` (the standard
  remedy), and document why.

The uncommitted `findById()` change will be kept **only if** it is part of the
real fix; otherwise the two WIP files are reverted so the tree is clean.

### Step C — Fix the separate custom-chord test

- Make "a custom chord is added to the toolbar" reliably open the dialog and find
  the "Add" `FilledButton`. Likely the same bounded-pump fix; confirm the dialog
  opens and the button is found.

### Step D — Guard against a 30-minute suite ever again

- Add a per-test timeout to the editor test file (e.g. a `timeout:
  Timeout(Duration(seconds: 30))` on the group or the slow tests) so a future
  regression fails in seconds, not 10 minutes.

## 4. Files to change

- `test/screens/song_editor_screen_test.dart` — fix the three hanging tests and
  the custom-chord test; add a per-test timeout. (Temporary probe test added and
  then removed during the work.)
- `lib/screens/song_editor_screen.dart` — only if Step A shows an app-side cause
  (loading spinner / rebuild loop).
- `lib/providers/song_editor_provider.dart` — only if the fix belongs here
  (keep, finish, or revert the WIP `findById()` change).
- `test/helpers/fake_song_repository.dart` — keep or revert its `findById()`
  addition to match the provider decision.

No production behaviour change is intended unless Step A proves an app bug; the
aim is correct, fast tests over the same code.

## 5. Verification

- `flutter analyze` clean.
- `flutter test test/screens/song_editor_screen_test.dart` passes in well under a
  minute (no 10-minute hang).
- Full `flutter test` completes in normal time with everything green.

## 6. Risks / notes

- This is a separate concern from Phase 5 (already complete). It touches editor
  files, not the auto-scroll work.
- If Step A shows a real app bug, fixing it may slightly change the editor's
  loading behaviour (no more full-screen spinner flash); that is an improvement,
  not a feature change.

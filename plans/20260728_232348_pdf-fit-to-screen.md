# Make the exported PDF easier to read (bigger text, no line splitting, open-at-fit hint)

**Status:** completed

## The issue

The user says the exported PDF is "not fit to screen" and the lyrics look too
small when the file is opened in any PDF app.

Two separate things are going on:

1. **The real cause — the text is small compared to the page.**
   The sheet is A4 portrait (595 x 842 pt) with 32 pt margins, 11 pt lyrics and
   8 pt chords. When a phone shows the whole A4 page, that 11 pt text becomes
   tiny. No viewer setting can fix this; the text has to be bigger *relative to
   the page*.

2. **The "fit to screen" flag.** A PDF can hold an `/OpenAction` telling the
   viewer to open zoomed so the page fits. The current export has none, because
   the Android `PrintDocumentAdapter` never writes one. Adding it helps desktop
   viewers (Adobe Reader, Foxit); most phone viewers ignore it. It is a hint,
   not a guarantee — worth adding, but it is not the main fix.

3. **Bigger text makes long lines wrap.** Today a long lyric line that does not
   fit the page width wraps onto a second line (`.line { flex-wrap: wrap }`).
   With 15 pt text this would happen much more often, which breaks up the song
   and is hard to follow while playing. The user asked that a lyric line should
   **not** split onto a second line wherever possible.

The user picked: **bigger text on A4**, **no line splitting**, *and* **add the
fit hint too**.

## The plan

### Part 1 — bigger text on A4

Change only the CSS in `PdfExportService._buildCss`. Page stays A4 portrait so
the sheet still prints correctly on paper.

| Item | Now | New | Why |
|------|-----|-----|-----|
| `@page` margin | 32 pt | 20 pt | Gives back about 24 pt of usable width |
| `.title` | 22 pt | 26 pt | Readable at a glance |
| `.artist` | 12 pt | 13 pt | Keeps its place under the title |
| `.meta` (Key/BPM) | 11 pt | 12 pt | Matches the artist line |
| `.piece .word` (lyrics) | 11 pt | 15 pt | The main change — about 36% bigger |
| `.piece .chord` | 8 pt | 11 pt | Chords stay clearly smaller than lyrics |
| `.chord` row height | 11 pt | 14 pt | Must grow with the chord font or chords clip |
| `.blank` (empty line) | 10 pt | 13 pt | Keeps verse spacing looking the same |
| `.line` bottom margin | 2 pt | 3 pt | Small breathing room at the bigger size |
| `body` line-height | 1.35 | 1.30 | Slightly tighter so we do not add too many pages |

Effect: text is roughly 36–40% bigger relative to the page, so it looks that
much bigger at any zoom level, in any PDF app. Cost: a long song may take one
or two more pages. That is expected and acceptable.

The multi-song export (`buildHtmlForMultiple`) shares the same CSS, so it gets
the change for free.

### Part 2 — keep each lyric line on one line

Bigger text alone would push many lines onto a second row. To stop that, each
line gets **shrunk just enough to fit**, on its own, instead of wrapping.

**CSS side** (in `PdfExportService._buildCss`):

- `.line` changes from `flex-wrap: wrap` to `flex-wrap: nowrap`, so a line no
  longer breaks by itself.
- Each `.line` gets its own font size through a CSS variable
  (`.line { font-size: var(--lc-line, 15pt) }`), and `.word` / `.chord` size
  themselves from that (`font-size: 1em` for words, `0.73em` for chords). This
  way one number per line scales both the lyric and its chords together.
- A `.line.wrapped` class turns wrapping back on, used only as the last resort
  below.

**Auto-fit script** (a small `<script>` written into the same HTML, so the file
stays fully self-contained and offline — no URL, no library):

For every `.line`, after the embedded fonts have loaded:

1. Measure it. If it already fits the page width, leave it alone.
2. If it is too wide, shrink that line's font size step by step (about 0.5 pt at
   a time) until it fits, down to a floor of **9 pt**.
3. If it still does not fit at 9 pt (a very long line), put the `wrapped` class
   on it so it wraps as it does today rather than running off the page.

So short and normal lines print at the full 15 pt, and only the few genuinely
long lines get quietly reduced — each one only as much as it needs. Chords stay
locked above their word because they shrink with it.

**Running it at the right moment** (`LcHtmlToPdf.kt`): the JavaScript the native
side already runs after `document.fonts.ready` gets one extra call first —
`if (window.lcFitLines) window.lcFitLines();` — then it signals `onReady()` as
before. Measuring must happen *after* the real fonts load, or the widths would
be wrong. If the function is missing (older HTML), the check simply skips it and
nothing breaks.

### Part 3 — the "open at fit" hint

The Android renderer hands back finished PDF bytes, so the hint has to be added
to those bytes afterwards.

New pure Dart service `lib/services/pdf_fit_action.dart` with one function:

```dart
Uint8List addFitToPageAction(Uint8List pdf)
```

How it works (safe, standard **incremental update** — it appends to the file
and never rewrites existing bytes, so all existing byte offsets stay valid):

1. Read the bytes as `latin1` (PDF structure is ASCII; this never corrupts the
   binary streams because we only append).
2. Find the last `startxref` value and the `trailer` dictionary.
3. From the trailer read `/Root N G R` — the catalog object number.
4. Find the catalog object `N G obj << ... >>` and read its dictionary.
5. If it already has an `/OpenAction`, return the bytes unchanged.
6. Find the first page: read `/Pages M G R`, then that node's `/Kids [ X G R
   ... ]`, walking down until an object whose dictionary has `/Type /Page`.
7. Append to the file:
   - a new version of the catalog object, same dictionary plus
     `/OpenAction [X 0 R /Fit]`,
   - a fresh `xref` section holding just that one object entry,
   - a `trailer` with the original `/Root` and `/Size`, plus `/Prev <old
     startxref>`,
   - `startxref <offset of the new xref>` and `%%EOF`.

`/Fit` means "fit the whole page in the window" — literally fit-to-screen.
(`/FitH` = fit width, which shows text bigger; it is a one-word change if the
user prefers it later.)

**Never breaks the export (CLAUDE.md hard rule 4).** Every step is wrapped so
that *any* surprise — a cross-reference *stream* instead of a table, a missing
`/Root`, an unparsable dictionary, an object-stream catalog — makes the function
return the **original bytes unchanged**. A worse-looking default zoom is never
worth a broken PDF.

### Part 4 — wire it in

Apply the patch in one place: `HtmlPdfService.convert`, right after the native
bytes come back and before they are returned. All four callers then get it
automatically:

- song page → Export PDF
- song page → Share as PDF
- song list → Export selected as PDF
- song list → Share selected as PDF

## Files to change

| File | Change |
|------|--------|
| `lib/services/pdf_export_service.dart` | New font sizes and margins in `_buildCss` (Part 1); `nowrap` + per-line `--lc-line` sizing in the CSS and the `lcFitLines` auto-fit `<script>` in the built HTML (Part 2). No structural change. |
| `android/app/src/main/kotlin/android/print/LcHtmlToPdf.kt` | Call `window.lcFitLines()` (guarded) after `document.fonts.ready`, before `onReady()` (Part 2). |
| `lib/services/pdf_fit_action.dart` | **New.** Pure `addFitToPageAction(Uint8List)` that appends the `/OpenAction [page /Fit]` incremental update, returning the input unchanged on any problem (Part 3). |
| `lib/services/html_pdf_service.dart` | Pass the native bytes through `addFitToPageAction` before returning (Part 4). |
| `test/services/pdf_export_service_test.dart` | Update/add checks for the new sizes (lyrics 15 pt, chords 11 pt, margin 20 pt), for `flex-wrap: nowrap`, and that the HTML defines `lcFitLines`. |
| `test/services/pdf_fit_action_test.dart` | **New.** Tests: adds `/OpenAction` to a small hand-built PDF; leaves a PDF that already has one alone; returns the input unchanged for junk bytes, empty bytes, and a PDF with no `/Root`. |

The page size and the screens are untouched.

## How to check it worked

1. `flutter analyze` — must be clean.
2. `flutter test` — all green.
3. On a device: export a song as PDF, open it, and confirm the lyrics are
   clearly bigger than before.
4. Export a song that has a long line and confirm it stays on **one** line
   (slightly smaller), with its chords still sitting over the right words.
5. Export a Malayalam song and confirm the letters still shape correctly (the
   font work is untouched, but the sizes changed).
6. Export several selected songs and confirm each song still starts on its own
   page, and that the auto-fit ran on every song, not just the first.

## Risks

- **More pages.** Bigger text means long songs may run to an extra page. This is
  the direct trade-off for readable lyrics.
- **Uneven line sizes.** Because each long line shrinks on its own, a page can
  hold lines at slightly different sizes. That is the cost of never splitting a
  line. The floor of 9 pt stops any line becoming unreadable.
- **Auto-fit adds render time.** The script measures every line once. For a very
  long song this adds a fraction of a second; the existing 20 s native timeout
  is far larger, so there is plenty of headroom.
- **PDF tests cannot run the script.** Unit tests only see the HTML, so they
  check that the script and the CSS are present. The shrinking itself must be
  confirmed on a device (check 4 above).
- **The fit hint may be ignored.** Many phone PDF apps pick their own zoom. Part
  1 is what actually makes the lyrics bigger; Part 2 is a bonus.
- **PDF byte patching.** Handled by returning the original bytes on any doubt,
  and covered by tests.

# Fix: performance view shows the wrong song after saving an edit

**Status:** completed

## The issue (what the user saw)

1. The user edited song A (Jingle Bells) and saved it.
2. Then the user edited song B (Untitled Song) and saved it.
3. Back on the performance view, the top bar shows song B's title, but the
   sheet below shows song A's lyrics and key.

## Root cause

The song list is sorted "newest activity first"
([song_list_provider.dart:31](../lib/providers/song_list_provider.dart#L31)).
Saving a song bumps its timestamp, so it jumps to the top of the list —
which also reorders the pager in the performance view.

The performance view's pager
([song_performance_screen.dart:110-117](../lib/screens/song_performance_screen.dart#L110-L117))
handles this: `_syncPager` builds a brand-new `PageController` with
`initialPage` pointing at the current song's index in the new order.

But `PageController.keepPage` defaults to `true`. That makes the new
controller ignore `initialPage` and instead restore the page index that
`PageStorage` saved for the old order. That old index now points at a
**different song** in the reordered list. And because the raw page number did
not change, `onPageChanged` never fires, so `_currentId` (which drives the
title bar) is not updated either. Result: title from song B, sheet from
song A.

## The fix

> **Correction found while implementing.** The first idea (`keepPage: false`)
> did not fix the bug — the new regression test still failed. The real cause
> is one step deeper: when `_syncPager` swaps in a brand-new `PageController`,
> Flutter's `Scrollable` keeps the *existing scroll position* and just
> re-attaches it to the new controller. So `initialPage` is never applied at
> all, and the pager stays at the old pixel offset while the list order
> changed underneath it.

The working fix: keep one `PageController` for the life of the screen, and
when the id list changes under a live pager, jump back to the current song's
new index after the frame settles:

```dart
if (_controller == null) {
  _controller = PageController(initialPage: index < 0 ? 0 : index);
  return;
}
WidgetsBinding.instance.addPostFrameCallback((_) {
  // ... jumpToPage(current song's new index) when it differs.
});
```

This also removes the old code's habit of disposing a controller that was
still attached to the pager. The jump lands on the song already on screen, so
`onPageChanged` either does not fire or sees the same id and returns early —
no settings reset happens.

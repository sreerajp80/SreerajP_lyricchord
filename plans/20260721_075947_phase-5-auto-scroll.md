# Plan — Phase 5: Auto-scroll

**Status:** completed

**Date:** 2026-07-21

Implements Phase 5 of [../docs/implementation_plan.md](../docs/implementation_plan.md):
hands-free scrolling of the chord sheet in two modes, added to the existing
Phase 4 performance view.

---

## 1. What is being asked (scope)

From the plan and [../docs/lyriccord_idea.md](../docs/lyriccord_idea.md) §Auto-scroll:

- **Manual Speed mode** — play/pause plus `0.5x / 1x / 2x` speed.
- **Tempo Auto mode** — user sets **BPM** and **length in measures**; the app
  computes the total **duration** and the **scroll speed (px/second)** so the
  sheet **ends exactly at the end of the song**. It shows the computed duration
  and px/s.
- Auto-scroll **stops itself** when it reaches the bottom.

**Definition of Done:** both modes scroll smoothly (within frame budget); Tempo
Auto ends at song end.

---

## 2. The issue / why work is needed

The performance view (Phase 4) shows the sheet in a plain, hand-scrolled
`SingleChildScrollView` inside `_SongPage`. There is no scroll controller, no
driver to advance the scroll over time, and no auto-scroll controls. The
`PerformanceControls` card already notes "Auto-scroll joins this card in Phase 5".

There is also no pure "scroll math" service, which the project's testing rules
call out as a critical area to cover.

---

## 3. Design decisions

- **Where the math lives:** a new **pure service** `AutoScrollCalculator` (no
  Flutter imports) holds all the timing math so it can be unit-tested. It exposes:
  - `tempoDuration(bpm, measures, {beatsPerMeasure = 4})` → `Duration`
    (`measures * beatsPerMeasure * 60 / bpm` seconds).
  - `tempoPixelsPerSecond(contentExtent, duration)` → `double`
    (`contentExtent / durationSeconds`, `0` when duration is 0).
  - `manualPixelsPerSecond(speedMultiplier)` → `double`
    (`baseManualPixelsPerSecond * speedMultiplier`).
  - Constant `baseManualPixelsPerSecond` (≈ 40 logical px/s at `1x`).
  This guarantees "ends exactly at song end": scrolling `contentExtent` px at
  `contentExtent / durationSeconds` px/s takes exactly `durationSeconds`.

- **Where the state lives:** a new provider `autoScrollProvider` holding
  `AutoScrollSettings` (immutable, `copyWith`), separate from
  `PerformanceSettings`. Fields:
  - `mode` — `AutoScrollMode.manual` or `AutoScrollMode.tempo`.
  - `speed` — one of `0.5 / 1.0 / 2.0` (manual mode).
  - `measures` — int, default 32, clamped to a sensible range (e.g. 1–512) for
    tempo mode.
  - `isPlaying` — whether the sheet is currently scrolling.
  Notifier methods: `setMode`, `setSpeed`, `increaseMeasures` / `decreaseMeasures`
  (or a setter), `play`, `pause`, `togglePlay`, `stop`, `resetAll`.
  Auto-scroll is view state (like `PerformanceSettings`): it is reset when the
  user swipes to another song.

- **Where the scrolling happens:** `_SongPage` in
  `song_performance_screen.dart` becomes a `ConsumerStatefulWidget`. It owns:
  - a `ScrollController` for its `SingleChildScrollView`, and
  - a `Ticker` (via `SingleTickerProviderStateMixin`) that, while playing,
    advances the scroll offset each frame by `pixelsPerSecond * dtSeconds`.
  It `ref.listen`s to `autoScrollProvider` to start/stop the ticker on
  play/pause. Each frame it clamps to `maxScrollExtent`; on reaching the bottom
  it calls `stop()` (auto-stop). The px/s used comes from `AutoScrollCalculator`
  using the live `maxScrollExtent` (tempo) or the speed multiplier (manual).
  The current px/s and duration are pushed back so the controls can show them
  (via a small computed field on the notifier, or read from the controller in
  the controls). Chosen approach: `_SongPage` writes the live `contentExtent`
  into the notifier (`reportContentExtent`) whenever layout settles, and the
  controls compute duration/px-s from the calculator for display. This keeps the
  controls widget free of scroll internals.

- **Controls UI:** a new widget `AutoScrollControls` (its own file) is added as
  the last section inside the `PerformanceControls` `ExpansionTile`. It shows:
  - a Manual / Tempo segmented toggle,
  - **Manual:** a play/pause button and `0.5x / 1x / 2x` choice chips,
  - **Tempo:** a play/pause button, a measures stepper (−/value/＋), and a read
    out of the computed **duration** (`m:ss`) and **px/s**.
  Keeping it a separate widget keeps `performance_controls.dart` small; it is
  slotted into the existing card.

- **Frame budget:** driving offset from a single `Ticker` and using
  `jumpTo`/`position.jumpTo` per frame (not per-frame `animateTo`) keeps it to
  one layout write per frame — smooth and cheap.

## 6. Risks / notes

- `maxScrollExtent` is only known after layout; the ticker reads it live each
  frame, so a font-size change mid-scroll is handled naturally.
- Switching mode or changing measures while playing recomputes px/s on the next
  frame — no restart needed.
- Reduced-motion / accessibility is a Phase 8 concern; not handled here.
